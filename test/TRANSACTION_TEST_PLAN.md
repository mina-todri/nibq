## 🔍 تفصيل الحالات الاختبارية

### **Test Case 1️⃣: ✅ Full Success - Multiple Products with Different Variants**

#### **الهدف:**

التأكد من أن العملية الذرية تعمل بشكل صحيح عند:

- إنشاء طلب يحتوي على منتجات متعددة
- كل منتج به متغيرات مختلفة (مثلاً: اللون والحجم)
- تقليل المخزون بدقة لكل متغير

#### **السيناريو:**

```
المنتج 1: قميص بمتغيرات
├── أحمر - S: مخزون = 15
└── أحمر - M: مخزون = 8

المنتج 2: بنطلون بمتغير واحد
└── أزرق - L: مخزون = 20

الطلب:
├── 5 قطع من "قميص أحمر - S"
└── 3 قطع من "بنطلون أزرق - L"
```

#### **مراحل التنفيذ:**

```
1. قراءة المنتجات (ضمن Transaction)
   ✓ المنتج 1 موجود → أحمر - S: 15، أحمر - M: 8
   ✓ المنتج 2 موجود → أزرق - L: 20
   ✓ الطلب غير موجود (جديد)

2. التحقق من المخزون
   ✓ أحمر - S: 15 >= 5 ✓
   ✓ أزرق - L: 20 >= 3 ✓

3. كتابة الطلب
   ✓ order_001 → orders collection

4. تحديث المخزون
   ✓ منتج 1 → أحمر - S: 15 - 5 = 10
   ✓ منتج 2 → أزرق - L: 20 - 3 = 17

5. Commit Transaction
   ✓ جميع التغييرات تُطبق بذرية
```

#### **التوكيدات (Assertions):**

```dart
✓ يجب وجود الطلب في Firestore
✓ مخزون أحمر - S = 10 (15 - 5)
✓ مخزون أزرق - L = 17 (20 - 3)
✓ أحمر - M لم يتغير (= 8)
```

#### **الفائدة الاختبارية:**

- يتحقق من صحة العملية الذرية الأساسية
- يثبت أن جميع التحديثات تحدث أو لا تحدث معاً
- يتحقق من حساب المخزون الصحيح

### **Test Case 2️⃣: ❌ Out of Stock - Insufficient Variant Stock**

#### **الهدف:**

التأكد من أن النظام يرفض الطلب إذا كان المخزون ناقصاً ولا ينشئ الطلب

#### **السيناريو:**

```
المنتج: حذاء رياضي
└── أسود - 42: مخزون = 5

محاولة الشراء:
└── 10 قطع من "حذاء أسود - 42"

المشكلة:
  المطلوب: 10
  المتاح:  5 ❌
  النقص:  5 قطع
```

#### **مراحل التنفيذ:**

```
1. قراءة المنتج (ضمن Transaction)
   ✓ حذاء موجود → أسود - 42: 5

2. التحقق من المخزون
   ✗ 5 >= 10 ? → FALSE
   → رمي Exception

3. Transaction Rollback
   ✗ لا يتم كتابة الطلب
   ✗ لا يتم تحديث المخزون
   ✗ جميع التغييرات تلغى تلقائياً
```

#### **التوكيدات:**

```dart
✗ يجب رفع Exception
✗ رسالة الخطأ تحتوي على "الكمية المتاحة"
✓ الطلب لم يُنشأ
✓ المخزون بقي = 5 (لم يتغير)
```

#### **الفائدة الاختبارية:**

- يتحقق من آلية الحماية من الأخطاء
- يثبت أن الـ Transaction توقف العملية فوراً عند الفشل
- يمنع بيع منتجات غير موجودة

### **Test Case 3️⃣: ⚡ Race Condition - Concurrent Purchase**

#### **الهدف:**

محاكاة محاولة عميلين (Alice و Bob) شراء آخر قطعة متبقية في نفس الوقت
والتأكد من أن Firestore Transaction منع بيع نفس المنتج لعميلين

#### **السيناريو:**

```
المنتج: هاتف ذكي نادر
└── ذهبي - 256GB: مخزون = 1 (آخر قطعة)

العميل 1 (Alice):
└── تحاول شراء 1 قطعة

العميل 2 (Bob):
└── يحاول شراء نفس الـ 1 قطعة في نفس الوقت
```

#### **الجدول الزمني للعمليات:**

```
الوقت  | Alice              | Bob               | المخزون الحالي
-------|-------------------|-------------------|---------------
T1    | قراءة: ذهبي=1      | -                 | 1
T2    | -                 | قراءة: ذهبي=1    | 1
T3    | تحديث: ذهبي=0     | -                 | 0
T4    | Commit            | -                 | 0 ✓
T5    | -                 | محاولة تحديث     | -
T6    | -                 | ❌ CONFLICT       | 0 (لم يتغير)
T7    | -                 | Abort/Retry      | -
```

#### **التوكيدات:**

```dart
✓ طلب Alice ينجح
✗ طلب Bob يفشل (Transaction Conflict)
✓ المخزون النهائي = 0
✓ Alice حصلت على الهاتف الوحيد
✗ Bob لا يحصل على شيء
```

#### **الفائدة الاختبارية:**

- يثبت أن Firestore Transactions تمنع Race Conditions
- يضمن عدم بيع نفس المنتج لعميلين
- يتحقق من العدالة في الشراء المتزامن

### **Test Case 4️⃣: 🔄 Rollback - Error During Order Write**

#### **الهدف:**

محاكاة فشل في أثناء العملية (مثل معرف مستخدم غير صالح)
والتأكد من أن Firestore يتراجع عن جميع التغييرات تلقائياً

#### **السيناريو:**

```
المنتج: قهوة
└── أسبريسو: مخزون = 100

محاولة الشراء:
├── userId: "" (فارغ - غير صالح ❌)
├── الكمية: 2 قطعة
└── المخزون: 100 ✓ (كافي)

المشكلة:
  ✓ المخزون كافي
  ✓ المنتج موجود
  ✗ userId فارغ → خطأ في بيانات الطلب
```

#### **مراحل التنفيذ:**

```
1. بداية Transaction

2. قراءة البيانات
   ✓ القهوة موجودة: أسبريسو = 100

3. التحقق من الصحة
   ✓ المخزون كافي: 100 >= 2

4. Validation - معرف المستخدم
   ✗ userId.isEmpty == true
   → رفع ArgumentError

5. Transaction Rollback
   ✗ لا يتم كتابة الطلب (لم يصل لهنا)
   ✗ لا يتم تحديث المخزون
   ✗ المخزون = 100 (لم يتغير)

6. Throw Exception → العملية فاشلة
```

#### **التوكيدات:**

```dart
✗ يجب رفع ArgumentError
✓ رسالة الخطأ تحتوي على "userId"
✗ الطلب لم يُنشأ (لم يصل للـ write phase)
✓ المخزون بقي = 100 (لم ينقص أبداً)
```

#### **الفائدة الاختبارية:**

- يثبت أن الـ Atomicity تحمي البيانات
- يتحقق من عدم إجزئة العملية (all or nothing)
- يضمن عدم تقليل المخزون إذا فشل الطلب

### **Test Case 5️⃣: 🛡️ Edge Cases**

#### **Subcase A: Product No Longer Exists**

```
السيناريو:
- المستخدم أضاف منتج للسلة
- بعد قليل، المالك حذف المنتج
- المستخدم يحاول دفع الطلب

النتيجة:
✗ الطلب يرفع Exception: "لم يعد متاحاً"
✓ لا توجد عملية شراء
```

#### **Subcase B: Default Variant (No Variant Selection)**

```
السيناريو:
- منتج بدون متغيرات محددة (مثل كتاب بنسخة واحدة)
- selectedVariant = "default"
- المخزون الحالي = 50

النتيجة:
✓ الطلب ينجح (لا حاجة لتحديث المخزون per-variant)
✓ المخزون بقي = 50 (الكود يتخطى update للـ default)
```

## 📝 ملاحظات مهمة

### **Mock vs Real Firestore:**

- الاختبارات تستخدم **Mock objects** (لا تتطلب Firebase حقيقي)
- للاختبار مع Firestore الحقيقي: استخدم **firebase_core_emulator**

### **Firestore Transaction Behavior:**

```dart
// إذا حدث خطأ أي نقطة → Automatic Rollback
await firestore.runTransaction((tx) async {
  // Point 1: قراءة
  final snap = await tx.get(ref); // ✓ نجح

  // Point 2: تحقق
  if (snap.data()['stock'] < qty) {
    throw Exception('Out of stock'); // ❌ خطأ هنا
    // ← جميع العمليات السابقة تُلغى تلقائياً
  }

  // Point 3: كتابة
  tx.set(...); // لن يصل هنا إذا حدث خطأ في Point 2

  // Point 4: تحديث
  tx.update(...); // لن يصل هنا إذا حدث خطأ في Point 2
});
```
